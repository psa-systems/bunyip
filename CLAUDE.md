# CLAUDE.md

Guidance for AI agents working in this repository.

## What this is

bunyip is the PSA Systems SaaS platform: a Cargo **workspace** with two server
apps plus the domain it owns.

```
bunyip/
├── bunyip-web/             bunyip-web - Axum SSR frontend (Maud + htmx). The browser-facing BFF.
├── bunyip-api/             bunyip-api - actix-web backend binary (wiring + main.rs + migrations).
└── crates/
    ├── bunyip-domain         models, repositories, business services, app Config, email templates.
    ├── bunyip-oci          OCI registry vertical.        (depends on bunyip-domain)
    └── bunyip-oidc         OIDC / OAuth 2.1 vertical.    (depends on bunyip-domain)
```

bunyip **owns all domain-specific code**. The generic, domain-free kernel
(errors, responses, validation, request_id/security_headers middleware, and the
generic jwt/encryption/password services) is `dunite-core`, consumed as a
**git dependency** from the Forgejo repo
`https://dev.a8n.run/psa-systems/dunite`. The dunite repo is anonymously
readable, so builds need no token (an optional `DUNITE_GIT_TOKEN` / buildkit
secret `dunite_token` is honoured for mirrors that require auth). Nothing in
dunite is bunyip-specific; nothing domain-specific lives in dunite.

All four dunite crates are pinned by `rev` (not `branch = "main"`), so moving
bunyip onto a newer dunite is an explicit one-line manifest diff in a bunyip PR
rather than a silent lockfile change (BUNYIP-426 F6). Bumping means editing the
`rev` in `crates/bunyip-{domain,oci,oidc}/Cargo.toml` and re-running
`cargo update --package dunite-core --package dunite-download --package dunite-oci --package dunite-oidc`.

Dependency direction (strictly downward): `bunyip-api -> bunyip-oci/oidc -> bunyip-domain -> dunite-core (git)`. `bunyip-web` is a standalone binary (talks to bunyip-api over /v1).

Ports: bunyip-api listens on `APP_PORT=4401`; bunyip-web on `4400`. bunyip-api
is also bunyip's OIDC issuer (it serves `/.well-known/*` + `/oauth2/*`).

## Build / dev

`just` drives everything (see `justfile`):

- `just dev` / `just dev-detach` - full local stack (postgres + api + web) via `compose.dev.yml`.
- `just dev-sso` - Traefik-routed stack on `*.a8n.run` (layers `compose.dev-sso.yml` on top). Cross-repo (bunyip + mokosh-server + mokosh-apps), Nebula topology, OIDC client registration, and every spin-up obstacle are documented in `docs/dev-sso-three-repo-runbook.md` - read it before touching dev-sso infra or onboarding a dev box.
- `just check` - fmt + clippy + build + docker builder stage. `just test`, `just typecheck`, `just lint`, `just fmt`.
- `just build-docker` - both production images (`build-docker-export` extracts the api static binary). `just migrate` / `migrate-revert`.
- `just create-release <major|minor|hotfix>` - bump `[workspace.package].version`, push the branch, open the release PR. The member-scoped `cargo update` that syncs `Cargo.lock` runs inside the pinned rust-builder image (dev boxes have no local cargo; online, to resolve the dunite-core git dep), NOT on the host; it is deliberately NOT `--workspace`, which would also roll the dunite git dep forward. Every git/fj step stays on the host, so the recipe needs docker (it fails fast if docker is missing).

Production runs the published images via `compose.yml` (api + web + postgres,
images under `dev.a8n.run/psa-systems-private/{bunyip-api,bunyip-web}`).

## Toolchain / checks on toolchain-less dev boxes

The canonical Rust toolchain is pinned in `rust-toolchain.toml` (currently
1.94.1, matching the `ghcr.io/niceguyit/rust-builder-*:v1.0.0-rust1.94-*`
images and CI). Bumping it means fixing any newly-promoted clippy/rustfmt
lints in the same PR so `just check` stays green everywhere.

Dev boxes have **no local Rust toolchain**, so run `just check-container`. It
wraps fmt + clippy + workspace lib tests in the pinned rust-builder image with
named cache volumes for the cargo registry and target dir (so repeated runs
stay incremental).

The image's rustup honours `rust-toolchain.toml`, so the pin (not the image
default) decides the compiler version. CI (`.forgejo/workflows/check.yml`)
runs the same fmt/clippy/build/test sequence on every PR and push to main.

## Critical conventions

- **sqlx**: only `bunyip-oidc` uses compile-time `sqlx::query!` macros. They resolve against the workspace-root `.sqlx/` offline cache; build with `SQLX_OFFLINE=true` (the justfile/Dockerfiles set it). After changing those queries, regenerate `.sqlx/` and commit it.
- **Migrations** live in `bunyip-api/migrations/` and run on api startup. **Committed migrations are immutable.** sqlx checksums every applied migration in `_sqlx_migrations` and a deployed database refuses to boot once a migration's on-disk content disagrees with the recorded checksum (`migration <version> was previously applied but has been modified`). Never edit, rename, or delete a migration already on `main`: fix forward with a NEW migration file. CI enforces this via `scripts/check-migration-immutability.nu` (BUNYIP-293); `scripts/reconcile-sqlx-checksums.md` covers recovering a DB that was broken by an in-place edit.
- **Email templates** are `include_str!`-compiled into `bunyip-domain`; the product name in every subject and in the template `app_name` context comes from the admin-managed branding record (see the branding bullet below), NOT from `APP_NAME`, which is only its bootstrap default. `BASE_URL` (`APP_URL`) stays env-derived.
- **Branding**: the product name, tagline, meta description and Open Graph image are ONE admin-managed row, `branding` (id = 1), and no product copy is compiled into either binary or set in compose (BUNYIP-561). `brand_name` resolves to the row value when non-empty, else bunyip-api's `APP_NAME` (a bootstrap default for a database that has never been branded); the other three resolve to the row value or to EMPTY, and empty means the markup is OMITTED - never substituted with a literal, because substituting one puts the copy back in the binary. `crates/bunyip-domain/src/models/branding.rs` owns the model, the validator and the `BrandingCache`; `EmailService` and `TotpService` read the name from that cache (so a rename reaches the next email subject and the next TOTP enrolment without a restart, and existing `user_totp` rows are never migrated). Public `GET /v1/branding` (under the `RateLimitFloor`, not in `EXEMPT_PATHS`) plus admin `GET`/`PUT /v1/admin/branding`; a `PUT` writes the row and refreshes the api-side cache in the same request, and every other api process re-reads it every 60s. bunyip-web has NO `APP_NAME` / `BRAND_DESCRIPTION`: `bunyip-web/src/branding.rs` fetches `/v1/branding` once before the listener binds (a failure logs `error` and serves unbranded) and refreshes every 60s (a failure logs `warn` and keeps the last good values), and `views::layout::document()` renders `og:`/`twitter:` metadata from it, each tag omitted when its source is empty. `scripts/check-brand-literals.nu` fails the build on a standalone `Bunyip` in `bunyip-web/src/{views,handlers,skin}/**/*.rs` unless the line carries a `// brand-literal-ok: <reason>` marker. Operator reference: `docs/configuration.md`.
- **Brand assets and the palette** (BUNYIP-560): the same record carries `theme_css` / `theme_color_light` / `theme_color_dark` plus three image slots, so a rebrand needs no rebuild. The images are rows in `branding_assets` (bytes in a `BYTEA`, the `user_avatars` pattern), uploaded through `POST`/`DELETE /v1/admin/branding/assets/{mark|favicon|mascot}` and served unauthenticated from `GET /v1/branding/assets/{kind}`, which bunyip-web proxies same-origin at `/brand/{kind}?v=<version>` (`branding::BRAND_ASSET_KINDS` is the allow-list that stops the path segment addressing another endpoint). The favicon slot stores what was uploaded as `favicon-source` and DERIVES the whole set from it in ONE transaction (`bunyip-api/src/branding_assets.rs`, the `image` crate, on the blocking pool per BUNYIP-553), so a half-replaced icon set is unreachable and one upload answers every `<link rel="icon">`. Fallbacks differ per slot and are stated in `views::layout::FAVICON_LINKS` / `brand_mark` / `skin::public::hero_mascot`: the favicon set falls back to the committed files under `bunyip-web/assets/` (root `/favicon.ico` included, served by `branding::favicon_ico`), the mark falls back to the built-in glyph, and the mascot has NO fallback - an unset slot renders no illustration rather than the previous product's. `BRAND_THEME_CSS` / `BRAND_THEME_COLOR_LIGHT` / `_DARK` survive as bootstrap defaults for one release and are removed in 0.16.0 (BUNYIP-568); the `#2f4e2e` / `#161a16` pair is gone from the binary, and `scripts/check-theme-colors.nu` now gates `bunyip-web/src/config.rs` as well as `views/layout.rs` so neither can carry a colour literal again.
- **Rate limiting**: `bunyip_api::rate_limit_floor::RateLimitFloor` applies `RateLimitConfig::API_UNAUTH` (per IP) / `API_AUTH` (per verified user) underneath every bunyip-api route, so a new endpoint is capped by default (BUNYIP-426 F7). Per-endpoint `check_rate_limit` calls are still the tight, specific control and run inside the floor; add one for anything auth-adjacent. Exemptions live in one list, `rate_limit_floor::EXEMPT_PATHS`. The cap in force (const -> env -> the persisted `rate_limit_configs` row, BUNYIP-413) is resolved through `RateLimitConfigRepository::effective`, which reads a process-wide 30-second snapshot of the whole table (`RateLimitConfigCache` in `crates/bunyip-domain/src/repositories/rate_limit_config.rs`, shaped on `PricingCache`), never a row per decision: the floor runs under every route, so the uncached read cost one extra query on every request and six more on every login (BUNYIP-556). `upsert` / `delete` invalidate the snapshot themselves, so an admin change is live on the next request in that process and within the TTL elsewhere; a refresh failure logs at `error` and keeps enforcing the last good snapshot rather than silently reverting to the compile-time caps. `effective_never_reads_a_row_per_decision` and `every_write_invalidates_the_snapshot` in that file fail the build if either half regresses.
- **Mailer relay**: `POST /v1/mailer/send` is the send-only API the other apps in the suite call instead of holding their own SMTP credentials (BUNYIP-602). The caller is a CALLING APP, not a person: it presents its `oauth_clients` machine credential (`client_id`:`client_secret`) as HTTP Basic, and `bunyip_oidc::machine_client` verifies it through the same `authenticate_client` the token endpoint uses, so a machine credential is registered, rotated and revoked in exactly one place. The secret is checked BEFORE the `client_credentials` entitlement, or the 403 becomes an oracle naming which registrations exist. `machine_client::load_machine_client` takes the pool rather than an `OidcProvider`, so the relay needs no issuer and no key material. The endpoint is in `rate_limit_floor::EXEMPT_PATHS` because the suite's apps share egress and the per-IP floor would let one app throttle another; `RateLimitConfig::MAILER_SEND` (60/min per `client_id`) and `MAILER_AUTH_FAILURES` (10/min per IP, failures only, read-only-checked ahead of the ~100 ms Argon2) are the controls that replace it. The `From:` identity is always this deployment's verified sending address, never the caller's, and a CR/LF in `to` or `subject` is refused rather than stripped. A deployment with no SMTP transport answers 502 and logs at `error`: the relay never takes a message and drops it, because the calling app has handed off responsibility for delivery. `EmailService::new_capturing` is the mocked transport the tests drive; `no_binary_wires_the_capturing_transport` in `bunyip-api/src/handlers/mailer.rs` fails the build if it reaches a binary. The suppression seam (`SuppressionList` / `NoSuppression` in `crates/bunyip-domain/src/services/mailer_relay.rs`) runs before every send and is filled by BUNYIP-603; provisioning tooling is BUNYIP-604. Operator reference: `docs/mailer-relay.md`.
- **One verification per request**: every access-token verification in bunyip-api goes through `bunyip_domain::middleware::verify_once`, which stashes the resulting `VerifiedIdentity` (the claims, plus the `users` row the at+jwt path read to build them) in the request extensions and answers every later call in that request from it (BUNYIP-557). The rate-limit floor resolves the caller underneath every non-exempt route and the handler's extractor resolves the same caller again, so an at+jwt used to pay two EdDSA verifications and two identical `SELECT ... FROM users` before the handler ran, and a handler self-read made it three. The fallback is not optional: the floor skips `EXEMPT_PATHS`, so an extractor may be the first caller and must verify for itself; `verify_either` is private and `nothing_calls_verify_either_outside_verify_once` in `crates/bunyip-domain/src/middleware/auth.rs` fails the build on a new caller that bypasses the cache. Only successes are cached, and the entry is tagged with the token it came from, so an unverifiable token still falls back to the tighter unauthenticated budget. A handler that re-reads the CALLER'S OWN row consults `middleware::request_user(&req)` first and keeps its `UserRepository::find_by_id` as the fallback (the HS256 cookie path verifies an HMAC and reads no row, so it caches none): `SuperAdminUser` and `handlers::application::resolve_has_member_access` do it inline, and every other handler self-read goes through `handlers::user::self_user` (BUNYIP-564), which adds an id guard so a cached row can never answer for another subject. `every_self_read_goes_through_the_request_scoped_row` in `bunyip-api/src/handlers/user.rs` fails the build on a new site that queries the caller's own row directly; its only exceptions are the post-write reads in `cancel_membership` / `cancel_membership_immediate`, which exist to observe a write made earlier in the same handler and so must stay plain queries. This does not weaken the freshness BUNYIP-229 added, because the row is still read from the database once per request, microseconds earlier, and nothing crosses a request boundary; a read that must observe a write made LATER in the same handler keeps its own query.
- **BFF chrome fetches**: the three near-static payloads bunyip-web reads on EVERY render (`/v1/pricing`, `/v1/applications` for the public footer, `/v1/auth/setup/status`) go through `TtlCache<T>` (`bunyip-web/src/ttl_cache.rs`), held on `AppState` and read ONLY via `AppState::{pricing, public_applications, setup_status, stripe_enabled}` (BUNYIP-518/555). A handler never fetches them directly: a per-render fetch turned ordinary browsing into a burst that exhausted the per-IP `RateLimitFloor` budget, and the 429 was swallowed into a thinner page (`/pricing` 404'd with pricing published, the footer lost its application links). On a failure the cache logs at `error` (endpoint + status + target) and serves the last good value; it returns `None` only when it has never read one, and the fallback is the caller's because it differs per payload (an unreadable setup status assumes payment IS configured). `public_applications` fetches WITHOUT the visitor's cookie, so one process-wide slot can never hold a per-user payload; `/dashboard` and `/applications` read the per-user `is_accessible` bit and therefore keep their own cookie-bearing fetch. `/v1/auth/setup/status` is in `EXEMPT_PATHS` (it is answered from process state and touches no table); `/v1/applications` stays floored because it reads the database. Independent post-guard fetches in a handler run under `tokio::join!`, never `try_join!`, which would collapse the per-fetch fallbacks into all-or-nothing. `chrome_fetch_guards` in `bunyip-web/src/web.rs` fails the build on a direct fetch or a serial fan-out.
- **Response compression**: `actix_web::middleware::Compress` is wrapped on the primary `HttpServer` stack in `bunyip-api/src/main.rs`, and `bunyip-web`'s `reqwest` carries the `gzip` feature so the BFF hop actually negotiates it (BUNYIP-559 F12; the admin lists gzip 6-8x, measured in `docs/api-performance-measurements.md`). actix's `Compress` has NO predicate API and does not exempt `text/event-stream`, so every streamed response on that stack calls `bunyip_api::compress::mark_uncompressed` (`Content-Encoding: identity`, which `Encoder::response` honours): `/v1/events` because compression defeats incremental delivery, and the release-asset download because encoding drops the handler's `Content-Length`. The OCI blob stream is exempt only because it is served by the separate `oci` `HttpServer`. `every_streamed_primary_response_is_compress_exempt` in `compress.rs` fails the build on a new `.streaming(` site without the marker or on the OCI vertical being mounted on the primary router.
- **Static assets and the first-load payload**: `bunyip-web`'s `/assets` is served `public, max-age=31536000, immutable`, so EVERY reference in the markup goes through `views::layout::asset()`, which appends the build-derived `?v=` (`ASSET_VERSION`, set by `bunyip-web/build.rs` from the short commit; `bunyip-web/oci-build/Dockerfile` must keep passing `GIT_COMMIT` into the BUILD stage, since `.dockerignore` excludes `.git`). An unversioned reference under that lifetime can never be updated; `every_shared_asset_reference_carries_the_build_version` in `layout.rs` fails the build on one. The root `/favicon.ico` is probed by URL rather than referenced from markup, so it cannot carry `?v=` and gets `public, max-age=86400` instead, never `immutable` (BUNYIP-560 moved that route to `branding::favicon_ico`, which keeps the header and follows the record). The rest of the rule set that keeps the first load small (BUNYIP-554): the hero is the admin-uploaded mascot served from the record and is NOT lazy (it is the LCP element), with the committed 448/718 WebP pair deleted in BUNYIP-560 since an unset slot renders no illustration; Inter and JetBrains Mono are the vendored variable builds under `assets/vendor/fonts/`, referenced from `input.css` with `font-display: swap`, which is why `security.rs` grants neither Google origin (`policy_grants_no_google_fonts_origin` gates it); Font Awesome is gone entirely and every glyph renders through `views::ui::icon` (`every_icon_name_used_in_the_views_resolves` fails the build on a name `inner()` does not know, because an unknown name renders a silently empty `<svg>`); and the avatar picker's CSS and controller ship ONLY from `handlers::dashboard_response_with_avatar_picker`, with the shared head carrying `AVATAR_SLOT_CSS` alone.
- **BFF response compression**: `bunyip-web`'s `CompressionLayer` runs `main.rs::compression_predicate()`, the `DefaultPredicate` plus a `NotForContentType` per archive type the release pipeline emits (`application/octet-stream`, `gzip`, `zip`, `x-tar`, `x-xz`). `DefaultPredicate` alone exempts only gRPC, `image/*`, `text/event-stream` and bodies under 32 bytes, so the BFF gzipped every byte of an already-compressed installer relayed by `handlers::dashboard::download_asset` for a ratio near 1.0 - and engaging the encoder drops the forwarded `Content-Length`, which is what killed the browser's download progress bar (BUNYIP-554 F4). Content type, not route, is the property that decides whether compression helps: a new binary payload type goes in that predicate.
- **Database pool sizing**: both pools are `DB_POOL_MAX_CONNECTIONS = 10` (`bunyip-api/src/main.rs`), a measured value, not a guess: at 250 concurrent browse sessions / 406 req/s the pool was never even checked out at sample time, and under a 6,500 req/s hammer it saturated without a single acquire timeout (BUNYIP-559 F10, `docs/api-performance-measurements.md`). The bound is PostgreSQL's own `max_connections`, and one api process opens TWO pools, so a replica costs `2 * DB_POOL_MAX_CONNECTIONS`. Raise it only when `acquire_timeouts` is non-zero, and raise PostgreSQL's limit in the same change. `DB_POOL_METRICS_INTERVAL_SECS` turns on the per-pool `size` / `idle` / `in_use` / `acquire_timeouts` sample line (`bunyip-api/src/db_metrics.rs`); the timeout counter itself is always collected.
- **Wire compatibility**: every field of a `Deserialize` response struct in `bunyip-web/src/api/types.rs` carries `#[serde(default)]` unless it is listed in the `ESSENTIAL_FIELDS` table of `scripts/check-serde-compat.nu` with its reason (identifiers, tokens and URLs whose absence must keep failing loudly). Wire enums decode through `String` via the `wire_enum!` macro, so an unrecognised value becomes `Unknown` rather than failing the response. Renaming a wire key follows expand/contract over two releases: release N emits both keys and the client reads the new one with `#[serde(alias = "<old>")]`; release N+1 drops the old key and the alias. The rule is asymmetric by direction - request structs in `bunyip-api/src/handlers/` keep required inputs required so a malformed request still 400s, and take the alias rule only. A 2xx body that will not decode logs `tracing::error!` with endpoint + target type and shows one fixed line (BUNYIP-506).
- **Cookies**: the `Secure` attribute comes from `Config::cookies_secure(&req)` (transport-derived), never from `Config::is_production()` (BUNYIP-426 F4). Any new set-cookie site must use it.
- **At-rest encryption**: ONE key, `APP_ENCRYPTION_KEY` (+ `APP_ENCRYPTION_KEY_PREV`, a comma-separated list of keys old rows still need, + `APP_KEY_VERSION`), protects `user_totp`, `stripe_config` and `email_config` alike (BUNYIP-483). `Config::app_key_set()` builds the one `AppKeySet`; every encrypt/decrypt site takes it. Rewrite existing rows with `bunyip-api reencrypt-secrets` (idempotent); `scripts/check-no-legacy-key-env.nu` fails the build if a per-consumer key name reappears. The list (rather than a single previous key) exists only for the consolidation window; narrowing it back to dunite's `EncryptionKeySet` is BUNYIP-491. Runbook: `docs/encryption-key-rotation.md`.
- **Startup config validation**: every environment variable bunyip-api reads is classified in ONE table, `ENV_INVENTORY` in `crates/bunyip-domain/src/config.rs` (BUNYIP-537), as required / required-in-production / feature-gating / defaulted, each with the feature it gates and a remediation sentence. `Config::from_env` collects EVERY failure in one pass and returns `ConfigError::Startup(Vec<ConfigFailure>)`; `main.rs` logs one `tracing::error!` per failure and exits 1. A missing feature-gating variable gets one `tracing::warn!` from `log_feature_gaps()` (so the "feature is off" message lives in the inventory, never at the call site); a defaulted one logs nothing. `panic!` is never the reporting mechanism for missing or malformed configuration: use `ConfigFailure` in the domain crate and `fatal_config_error` in `main.rs`. `bunyip-api/tests/env_inventory.rs` fails the build on an unclassified `env::var("...")` / `secret_env("...")` read, on a `panic!` returning to those two files, and on a boot report that does not exit 1. Operator-facing rendering: `docs/configuration.md`.
- **Secret sourcing (two tiers)**: Group-1 startup secrets (postgres, `DATABASE_URL`, `APP_ENCRYPTION_KEY`, `JWT_SECRET`, ...) are file-based: the app reads `/run/secrets/*` via the `{NAME}_FILE` convention (BUNYIP-38), provided directly by `scripts/init-secrets.nu` (dev throwaways) or the SOPS `compose-secrets.yml` on the docker hosts. They cannot be governed by the switch below (the database cannot hold the credential used to reach the database), are never fetched from or synced with Infisical, and so Infisical is never needed to boot. Group-2 governed integration secrets are exactly the three with more than one possible store (`SMTP_PASSWORD`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`), and ONE required variable declares which store holds them: `SECRETS_STORAGE=environment|database|infisical` (BUNYIP-542). The declared store is the ONLY one consulted; the old DB-then-env-then-Infisical precedence chain is deleted, not reordered. At boot each governed secret is used if the declared store holds it, warns (feature off) if no store does, warns per duplicate if another store also holds it, and is FATAL if the declared store is empty while another store holds it. `environment` mode reads `{NAME}_FILE` only (never the plain variable, which `docker inspect` exposes) and is the one read-only store, so the admin secret fields render read-only and the API answers 409; `database` and `infisical` mode write through to the declared store and hot-reload. `infisical` mode is fail-closed at boot; the other two never contact Infisical. `crates/bunyip-domain/src/config.rs` owns `SecretsStorage` / `GovernedSecret`, `bunyip-api/src/secrets.rs` owns every store read and write plus the `bunyip-api secrets-status` / `secrets-migrate --to <mode>` / `secrets-purge --confirm` pre-flight family. Runbook: `docs/secrets-infisical.md`; per-mode reference: `docs/configuration.md`.
- **Argon2 off the workers**: every request-path password hash and verify goes through `crates/bunyip-domain/src/services/argon2_offload.rs` (`hash_password` / `verify_password`, or `offload()` for a multi-hash loop), which runs the work on the blocking pool (BUNYIP-553). actix pins a connection to one worker arbiter and never moves its futures, so a ~100 ms Argon2 on the request future stalls every other request on that arbiter, `/v1/health` included. A multi-hash loop goes in ONE blocking task, never one task per iteration: `verify_recovery_code`'s up-to-8 verifies, `generate_and_store_recovery_codes`'s 8 hashes and `seed::load`'s per-user hashes each spawn once. A `JoinError` is logged at `error` and returned as an internal error, never collapsed into "wrong password". The parameters are unchanged (64 MiB / t=3 / p=4 for passwords, 19 MiB / t=2 / p=1 for recovery codes and the OIDC client secret); only where the cost is paid moved. The two sites that build a raw `Argon2` for their own preset (`totp.rs`, `authenticate_client` in `bunyip-oidc/src/handlers/oidc.rs`) do it inside an `offload` closure; everything else goes through `PasswordService`. `AuthService::password` survives for the strength / email-containment checks only. Two sites are exempt because no arbiter exists yet: `main.rs`'s `SETUP_DEFAULT_ADMIN` bootstrap and the `bunyip-api` test fixtures. `scripts/check-argon2-offload.nu` gates the shapes in `check.yml`; `an_offloaded_hash_leaves_the_arbiter_free` in `argon2_offload.rs` fails the build if the work returns to the request future.
- **Single-use tokens** are consumed by a guarded `UPDATE ... WHERE id = $1 AND used_at IS NULL` whose `rows_affected` decides the race; the caller branches on the returned bool before doing side-effecting work (BUNYIP-426 F9). A unit test in `repositories/token.rs` fails the build if an unguarded consume reappears.
- **Images**: bunyip-api is a musl-static build (`rust-builder-musl` base, governance `Dockerfile.oci-musl` pattern); bunyip-web is glibc (`rust-builder-glibc` base, needs bun + tailwind), governance `Dockerfile.oci-glibc` pattern. Both pass `GIT_COMMIT` / `GIT_TAG` / `BUILD_DATE` build args; tags come from `oci-build/get-tags.nu`. Both `oci-build/Dockerfile`s stage dependencies with cargo-chef (`chef` / `planner` / builder), each cook scoped to its own binaries (`--bin bunyip-web`; `--bin bunyip-api --bin bunyip-e2e-bootstrap`) so neither image compiles the other's dependency set: BUNYIP-389 for the api, BUNYIP-558 for the web, where a one-line source edit had been recompiling all 153 crates because the cargo cache mounts hold downloads, not artifacts. In the web image `bun run build:css` stays AFTER the source copy, since Tailwind scans the Rust sources for class names. Every external `FROM` in both Dockerfiles carries `tag@sha256:<digest>` (BUNYIP-426 F10); the api runtime tracks the same Alpine release `compose.yml` pins for postgres. Re-resolve a digest with `docker buildx imagetools inspect <ref> --raw | sha256sum` when bumping a tag, and change both halves together. Every buildkit cargo cache mount carries a per-image `id=` (`bunyip-{api,web}-cargo-{registry,git}`) and `sharing=locked` (BUNYIP-534): the publish workflows share one buildkit instance and a release commit fires both a `main` push and a `v*` tag push, so an unnamed shared mount (keyed by target path alone) let concurrent builds unpack crates into one directory and fail with `.cargo-ok: File exists`. Cargo's `.package-cache` lock sits at `$CARGO_HOME/.package-cache`, outside the mount, so it cannot serialise them. `scripts/check-cache-mount-sharing.nu` gates every Dockerfile in `check.yml`.
- **Workflow shell**: every `run:` step in `.forgejo/workflows/` executes under Nushell. Each job declares it once (`defaults.run.shell: nu {0}`) instead of per step, so a new step cannot inherit Bash; `scripts/check-workflow-shell.nu` gates both halves in `check.yml` (BUNYIP-489). Nushell has no backslash line continuation, so multi-line commands stay on one line.
- **Scripts are Nushell**: every script under `scripts/` (the CI guards plus the operator scripts) is a `#!/usr/bin/env nu` script, not Bash (BUNYIP-490). Nushell `0.112.2` is a documented prerequisite (`docs/getting-started.md`) and is present on the runners. `scripts/check-no-bash.nu` fails the build on any `.sh` file or POSIX-shell shebang under `scripts/`.
- **Scrollbars**: every scroll container keeps a scrollbar that is visible at rest, 14px on its cross axis, and coloured from the theme tokens (`--muted` / `--muted-foreground`), styled once globally at the end of `bunyip-web/input.css` (BUNYIP-509). No auto-hide, fade, overlay or hover-to-reveal behaviour, and never `scrollbar-width: thin` or `::-webkit-scrollbar { display: none }`. Editing `input.css` means rebuilding the committed `bunyip-web/assets/styles.css` (`bun run build:css` in `bunyip-web/`) in the same PR; `scripts/check-scrollbars.nu` gates both files in `check.yml`.
- **UI copy**: one name per admin section in Title Case across the sidebar (`admin_items()` in `bunyip-web/src/views/layout.rs`), the topbar title (the `admin_response` argument) and the page h1; route paths never move with a rename. Ellipses are the single-character `…`, never three dots, and empty states are terse noun phrases with no emoticon and no apology (BUNYIP-551). `scripts/check-ui-copy.nu` gates the last two in `check.yml`; a unit test in `layout.rs` gates the casing.
- **Prices and deadlines in copy**: a price a user reads comes from the published `/v1/pricing` payload, never a literal: `util::entry_price` is the cheapest monthly tier a visitor can still buy (lifetime and sold-out tiers excluded) and prices the signup card and the membership-required page; `util::tier_price` prices the member's own tier on the plan card, except when `price_locked`, where the member's `locked_price_amount` wins because a locked price is exactly the one the current tier price need not equal. The past-due dunning banner (`dunning_banner` in `handlers/dashboard.rs`) names that member's `grace_period_end`, not the fixed "within 30 days" it used to promise. Absent value means NO number, never a substituted one: "Get access to all tools", "See pricing", "before your grace period ends" (BUNYIP-590). `scripts/check-price-literals.nu` fails the build on a price per period or a `within N days` in any string literal under `bunyip-web/src` or `crates/web-kit/src` unless the line carries a `// price-literal-ok: <reason>` marker, and gates it in `check.yml`.
- **Password inputs**: every form where a user types a password renders `views::password::password_field`, so the characters can be revealed and checked (BUNYIP-282), and every form where a user CHOOSES one also carries `data-pw-guard` plus `views::password::guard_message()` and `script()` (BUNYIP-575). A rejected password change answers with a redirect, and a redirect re-renders every `type=password` input EMPTY (a server-known password is never written back into HTML), so `assets/js/password-field.js` refuses the submit while a rule the browser can check itself is broken and names that rule inline instead; `handlers::password_ok` stays the backstop for a client with no JS. The live per-rule indicators and the HaveIBeenPwned lookup stay in the separate `assets/js/password.js`, which gates its submit button on that lookup, so a form can take the toggle and the guard without also depending on an external service. `every_card_that_sets_a_password_reveals_it_and_guards_the_submit` in `handlers/auth_pages.rs` and the two `change_password_form_*` tests in `handlers/dashboard.rs` fail the build if a surface loses either half.
- **Authenticated navigation**: both app shells build their nav from one list, `shell_nav_sections()` in `bunyip-web/src/views/layout.rs`, rendered by `nav_links()` into two surfaces: the `hidden md:flex` `sidebar()` and the `md:hidden` `mobile_nav()` disclosure in `app_topbar` (BUNYIP-547). The sidebar is not rendered below 768px, so an entry added anywhere but that shared list is unreachable on a phone. `mobile_nav` is a `<details data-menu>`, the same pattern `profile_menu` uses, so `assets/js/app.js` already dismisses it on click-away and Escape; no new script. `every_authenticated_shell_navigates_below_the_md_breakpoint` in `layout.rs` strips the sidebar from each shell's markup and asserts every nav `href` still renders.
- **Theme tokens**: every surface is painted from the semantic tokens, client-side markup included. The toast pills in `bunyip-web/assets/js/app.js` use the same token pair as their server-rendered counterparts (success the `success` badge in `views/ui.rs`, error the offline banner in `server_status.rs`, info the popover surface), so they track `.dark` and `.high-contrast`; `input.css` remaps only `indigo` and `teal`, so any other stock Tailwind scale is a colour no theme class reskins. The framework shell (`document()` in `views/layout.rs`) carries no colour literal: the two `theme-color` metas come from `Config::theme_color_light` / `theme_color_dark` (`BRAND_THEME_COLOR_LIGHT` / `BRAND_THEME_COLOR_DARK`), whose defaults live in `bunyip-web/src/config.rs`, so a skin moves the browser chrome with the rest of the palette (BUNYIP-549). `scripts/check-theme-colors.nu` gates both in `check.yml`; a unit test in `layout.rs` gates the metas. Changing a class name in `assets/js/` means rebuilding the committed `bunyip-web/assets/styles.css` in the same PR, exactly as editing `input.css` does.
- **Amber contrast**: amber is the one stock scale the views paint text in, and a tint of it (`bg-amber-500/<n>`) lightens the surface under that text, so the ratio is measured against the composite, not the bare surface. Light halves use `amber-800` on a tint and `amber-700` bare; dark halves use `amber-300` / `amber-400` (BUNYIP-548). `every_amber_text_use_meets_aa` in `views/ui.rs` scans every source line carrying an amber text class and asserts AA 4.5:1 over `--card` and `--background` in all four theme blocks, reading the palette from the built `assets/styles.css`, so a new amber surface fails the build rather than shipping under AA.
- **Fetched list states**: every surface that renders a fetched collection tells three states apart, in this order: `@if !reachable { error_box("Could not reach the API to load <thing>.") } @else if items.is_empty() { empty_state(...) } @else { ... }`. `reachable` is the `data.is_ok()` flag kept beside the `unwrap_or_default()` at the fetch site (BUNYIP-461 for the admin lists, BUNYIP-546 for the member and public ones). A card is never hidden on failure or on empty: hiding it makes "could not load" and "nothing configured" indistinguishable from "everything is fine". Substituting an empty page for a failed fetch is the same defect in another shape, so `handlers/dashboard.rs` passes `Option<&PaginatedResponse<_>>` into its card bodies and `no_empty_page_fallback_absorbs_a_fetch_error` fails the build if that fallback returns. A fetch that only decorates another list (application groups, per-product downloads) may degrade silently in the UI, but logs `tracing::warn!` naming the degradation.
