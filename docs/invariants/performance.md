# Performance and caching

Full text of the performance and caching conventions indexed in [`CLAUDE.md`](../../CLAUDE.md#critical-conventions), moved here verbatim (BUNYIP-854).

## Rate limiting (BUNYIP-426, BUNYIP-413, BUNYIP-645, BUNYIP-556)

**Rate limiting**: `bunyip_api::rate_limit_floor::RateLimitFloor` applies `RateLimitConfig::API_UNAUTH` (per IP) / `API_AUTH` (per verified user) underneath every bunyip-api route, so a new endpoint is capped by default (BUNYIP-426 F7). Per-endpoint `check_rate_limit` calls are still the tight, specific control and run inside the floor; add one for anything auth-adjacent. Exemptions live in one list, `rate_limit_floor::EXEMPT_PATHS`. The cap in force is resolved through `RateLimitConfigRepository::effective`, which walks the declared configuration providers (`database` > `file` > `environment`, then the compile-time cap: BUNYIP-413/645) and reads a process-wide 30-second snapshot of the whole table (`RateLimitConfigCache` in `crates/bunyip-domain/src/repositories/rate_limit_config.rs`, shaped on `PricingCache`), never a row per decision: the floor runs under every route, so the uncached read cost one extra query on every request and six more on every login (BUNYIP-556). `upsert` / `delete` invalidate the snapshot themselves, so an admin change is live on the next request in that process and within the TTL elsewhere; a refresh failure logs at `error` and keeps enforcing the last good snapshot rather than silently reverting to the compile-time caps. Layering the providers and resolving every preset through them is part of BUILDING that snapshot, so a decision is a map lookup: the `rate_limit_configs` rows are the `DatabaseProvider` for the `RATE_LIMIT_{ACTION}_MAX_REQUESTS` / `_WINDOW_SECONDS` keys and nothing more, and `bunyip-api config-status` reports the per-action provenance (BUNYIP-645). Those keys are the one GENERATED part of `CONFIG_KEYS` and `ENV_INVENTORY`, one pair per `RateLimitConfig::ALL` entry (`models::rate_limit::rate_limit_vars`), because the names are built from the action; `every_rate_limit_action_declares_both_of_its_keys` and `the_rate_limit_path_reads_no_provider_of_its_own` fail the build if an action loses its declaration or a private environment layer comes back. `effective_never_reads_a_row_per_decision` and `every_write_invalidates_the_snapshot` in that file fail the build if either half regresses.

## One verification per request (BUNYIP-557, BUNYIP-564)

**One verification per request**: every access-token verification in bunyip-api goes through `bunyip_domain::middleware::verify_once`, which stashes the resulting `VerifiedIdentity` (the claims, plus the `users` row the at+jwt path read to build them) in the request extensions and answers every later call in that request from it (BUNYIP-557). The rate-limit floor resolves the caller underneath every non-exempt route and the handler's extractor resolves the same caller again, so an at+jwt used to pay two EdDSA verifications and two identical `SELECT ... FROM users` before the handler ran, and a handler self-read made it three. The fallback is not optional: the floor skips `EXEMPT_PATHS`, so an extractor may be the first caller and must verify for itself; `verify_either` is private and `nothing_calls_verify_either_outside_verify_once` in `crates/bunyip-domain/src/middleware/auth.rs` fails the build on a new caller that bypasses the cache. Only successes are cached, and the entry is tagged with the token it came from, so an unverifiable token still falls back to the tighter unauthenticated budget. A handler that re-reads the CALLER'S OWN row consults `middleware::request_user(&req)` first and keeps its `UserRepository::find_by_id` as the fallback (the HS256 cookie path verifies an HMAC and reads no row, so it caches none): `SuperAdminUser` and `handlers::application::resolve_has_member_access` do it inline, and every other handler self-read goes through `handlers::user::self_user` (BUNYIP-564), which adds an id guard so a cached row can never answer for another subject. `every_self_read_goes_through_the_request_scoped_row` in `bunyip-api/src/handlers/user.rs` fails the build on a new site that queries the caller's own row directly; its only exceptions are the post-write reads in `cancel_membership` / `cancel_membership_immediate`, which exist to observe a write made earlier in the same handler and so must stay plain queries. This does not weaken the freshness BUNYIP-229 added, because the row is still read from the database once per request, microseconds earlier, and nothing crosses a request boundary; a read that must observe a write made LATER in the same handler keeps its own query.

## BFF chrome fetches (BUNYIP-518, BUNYIP-555, BUNYIP-667)

**BFF chrome fetches**: the two near-static payloads bunyip-web reads on EVERY public render (`/v1/pricing`, `/v1/auth/setup/status`) go through `TtlCache<T>` (`bunyip-web/src/ttl_cache.rs`), held on `AppState` and read ONLY via `AppState::{pricing, setup_status, stripe_enabled}` (BUNYIP-518/555). A handler never fetches them directly: a per-render fetch turned ordinary browsing into a burst that exhausted the per-IP `RateLimitFloor` budget, and the 429 was swallowed into a thinner page (`/pricing` 404'd with pricing published, the footer lost its application links). On a failure the cache logs at `error` (endpoint + status + target) and serves the last good value; it returns `None` only when it has never read one, and the fallback is the caller's because it differs per payload (an unreadable setup status assumes payment IS configured). `/v1/applications` (`AppState::public_applications`) sits on the same `TtlCache` on the same terms - fetched WITHOUT the visitor's cookie, so one process-wide slot can never hold a per-user payload, and no public surface that reads it may touch a per-visitor field (`is_accessible`, `maintenance_mode`) - but it is NO LONGER a public-chrome payload: the public header and footer stopped rendering per-application entries in BUNYIP-667/682, so the list now feeds only the landing page's application cards (`skin/public::landing`) and the two `/apps/{slug}/docs` handlers as the fallback for their app-name display. BUNYIP-683 removed the fetch from `public_ctx` and from every public-shell caller, so a rendering path that no longer reads the list also no longer pays for its cache read. `/dashboard` and `/applications` read the per-user `is_accessible` bit and therefore keep their own cookie-bearing fetch. `/v1/auth/setup/status` is in `EXEMPT_PATHS` (it is answered from process state and touches no table); `/v1/applications` stays floored because it reads the database. Independent post-guard fetches in a handler run under `tokio::join!`, never `try_join!`, which would collapse the per-fetch fallbacks into all-or-nothing. `chrome_fetch_guards` in `bunyip-web/src/web.rs` fails the build on a direct fetch or a serial fan-out. `/v1/application-docs` (the `/docs` hub's documented-application list, `AppState::documented_apps`, BUNYIP-635) rides the same `TtlCache` on the same terms, but is read only by the four `/docs` and `/apps/{slug}/docs` handlers rather than by every render, so it is not one of the chrome payloads that guard covers.

## Response compression (BUNYIP-559)

**Response compression**: `actix_web::middleware::Compress` is wrapped on the primary `HttpServer` stack in `bunyip-api/src/main.rs`, and `bunyip-web`'s `reqwest` carries the `gzip` feature so the BFF hop actually negotiates it (BUNYIP-559 F12; the admin lists gzip 6-8x, measured in `docs/api-performance-measurements.md`). actix's `Compress` has NO predicate API and does not exempt `text/event-stream`, so every streamed response on that stack calls `bunyip_api::compress::mark_uncompressed` (`Content-Encoding: identity`, which `Encoder::response` honours): `/v1/events` because compression defeats incremental delivery, and the release-asset download because encoding drops the handler's `Content-Length`. The OCI blob stream is exempt only because it is served by the separate `oci` `HttpServer`. `every_streamed_primary_response_is_compress_exempt` in `compress.rs` fails the build on a new `.streaming(` site without the marker or on the OCI vertical being mounted on the primary router.

## Static assets and the first-load payload (BUNYIP-560)

**Static assets and the first-load payload**: `bunyip-web`'s `/assets` is served `public, max-age=31536000, immutable`, so EVERY reference in the markup goes through `views::layout::asset()`, which appends the build-derived `?v=` (`ASSET_VERSION`, set by `bunyip-web/build.rs` from the short commit; `bunyip-web/oci-build/Dockerfile` must keep passing `GIT_COMMIT` into the BUILD stage, since `.dockerignore` excludes `.git`). An unversioned reference under that lifetime can never be updated; `every_shared_asset_reference_carries_the_build_version` in `layout.rs` fails the build on one. The root `/favicon.ico` is probed by URL rather than referenced from markup, so it cannot carry `?v=` and gets `public, max-age=86400` instead, never `immutable` (BUNYIP-560 moved that route to `branding::favicon_ico`, which keeps the header and follows the record). The rest of the rule set that keeps the first load small (BUNYIP-554): the hero is the admin-uploaded mascot served from the record when the slot is set, else the committed 448/718 WebP pair under `bunyip-web/assets/` (deleted in BUNYIP-560, restored in BUNYIP-605), and is NOT lazy either way since it is the LCP element; Inter and JetBrains Mono are the vendored variable builds under `assets/vendor/fonts/`, referenced from `input.css` with `font-display: swap`, which is why `security.rs` grants neither Google origin (`policy_grants_no_google_fonts_origin` gates it); Font Awesome is gone entirely and every glyph renders through `views::ui::icon` (`every_icon_name_used_in_the_views_resolves` fails the build on a name `inner()` does not know, because an unknown name renders a silently empty `<svg>`); and the avatar picker's CSS and controller ship ONLY from `handlers::dashboard_response_with_avatar_picker`, with the shared head carrying `AVATAR_SLOT_CSS` alone.

## BFF response compression (BUNYIP-554)

**BFF response compression**: `bunyip-web`'s `CompressionLayer` runs `main.rs::compression_predicate()`, the `DefaultPredicate` plus a `NotForContentType` per archive type the release pipeline emits (`application/octet-stream`, `gzip`, `zip`, `x-tar`, `x-xz`). `DefaultPredicate` alone exempts only gRPC, `image/*`, `text/event-stream` and bodies under 32 bytes, so the BFF gzipped every byte of an already-compressed installer relayed by `handlers::dashboard::download_asset` for a ratio near 1.0 - and engaging the encoder drops the forwarded `Content-Length`, which is what killed the browser's download progress bar (BUNYIP-554 F4). Content type, not route, is the property that decides whether compression helps: a new binary payload type goes in that predicate.

## Database pool sizing (BUNYIP-559)

**Database pool sizing**: both pools are `DB_POOL_MAX_CONNECTIONS = 10` (`bunyip-api/src/main.rs`), a measured value, not a guess: at 250 concurrent browse sessions / 406 req/s the pool was never even checked out at sample time, and under a 6,500 req/s hammer it saturated without a single acquire timeout (BUNYIP-559 F10, `docs/api-performance-measurements.md`). The bound is PostgreSQL's own `max_connections`, and one api process opens TWO pools, so a replica costs `2 * DB_POOL_MAX_CONNECTIONS`. Raise it only when `acquire_timeouts` is non-zero, and raise PostgreSQL's limit in the same change. `DB_POOL_METRICS_INTERVAL_SECS` turns on the per-pool `size` / `idle` / `in_use` / `acquire_timeouts` sample line (`bunyip-api/src/db_metrics.rs`); the timeout counter itself is always collected.

## Argon2 off the workers (BUNYIP-553)

**Argon2 off the workers**: every request-path password hash and verify goes through `crates/bunyip-domain/src/services/argon2_offload.rs` (`hash_password` / `verify_password`, or `offload()` for a multi-hash loop), which runs the work on the blocking pool (BUNYIP-553). actix pins a connection to one worker arbiter and never moves its futures, so a ~100 ms Argon2 on the request future stalls every other request on that arbiter, `/v1/health` included. A multi-hash loop goes in ONE blocking task, never one task per iteration: `verify_recovery_code`'s up-to-8 verifies, `generate_and_store_recovery_codes`'s 8 hashes and `seed::load`'s per-user hashes each spawn once. A `JoinError` is logged at `error` and returned as an internal error, never collapsed into "wrong password". The parameters are unchanged (64 MiB / t=3 / p=4 for passwords, 19 MiB / t=2 / p=1 for recovery codes and the OIDC client secret); only where the cost is paid moved. The two sites that build a raw `Argon2` for their own preset (`totp.rs`, `authenticate_client` in `bunyip-oidc/src/handlers/oidc.rs`) do it inside an `offload` closure; everything else goes through `PasswordService`. `AuthService::password` survives for the strength / email-containment checks only. Two sites are exempt because no arbiter exists yet: `main.rs`'s `SETUP_DEFAULT_ADMIN` bootstrap and the `bunyip-api` test fixtures. `scripts/check-argon2-offload.nu` gates the shapes in `check.yml`; `an_offloaded_hash_leaves_the_arbiter_free` in `argon2_offload.rs` fails the build if the work returns to the request future.
