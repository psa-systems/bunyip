# Configuration, secrets and feature flags

Full text of the configuration, secrets and feature flags conventions indexed in [`CLAUDE.md`](../../CLAUDE.md#critical-conventions), moved here verbatim (BUNYIP-854).

## Feature flags (BUNYIP-493, BUNYIP-487)

**Feature flags**: a NEW switch that hides an unbuilt or optional surface is a `Feature` variant in the ONE registry, `crates/bunyip-domain/src/feature_toggles.rs` (BUNYIP-840), stored as a `feature_toggles` row (a missing row reads as OFF) and flipped on the admin Feature Toggles page (`/admin/features`; `GET /v1/admin/feature-toggles` for any admin, `PUT /v1/admin/feature-toggles/{key}` super-admin-only, audited in the same transaction, 404 on an unknown key). Adding one needs no migration, admin form or probe field; never add a new `tier_config` flag column. bunyip-api holds the rows in a process-wide `Arc<RwLock<FeatureToggles>>` (`FeatureToggleSnapshot`) loaded at startup, re-read every 60s and refreshed at once by the process that served a save; `GET /v1/auth/setup/status` publishes every key as `features` from it, and bunyip-web installs that map next to `orgs_enabled` and reads it through `feature_enabled(key)`. `no_other_provider_can_turn_a_feature_on` fails the build if a toggle key leaks into `CONFIG_KEYS`, `ENV_INVENTORY` or the file layer. Operator and developer reference: `docs/feature-toggles.md`. The two legacy switches stay admin-managed columns on `tier_config` (`pricing_enabled`, `orgs_enabled`; moving pricing in is BUNYIP-841), never an env variable and never a compile-time constant, so they are reversible per environment with no deploy. Off means INVISIBLE, not inert: with `pricing_enabled` off `/pricing` 404s and every link to it is hidden, and with `orgs_enabled` off `/organizations` answers the branded 404 BEFORE the auth guard (a redirect to `/login` would confirm the route) and its nav entry is not rendered at all (BUNYIP-493). The api publishes `orgs_enabled` on the public feature-flags probe `GET /v1/auth/setup/status`, answered from the process-wide `Arc<RwLock<TierConfig>>` the admin save hot-reloads, so the probe still touches no table and stays in `EXEMPT_PATHS`. bunyip-web reads that probe in `feature_flags.rs` (one bounded read before the listener binds, then every 60s, the branding shape) and installs it into `web_kit::shell`'s process-wide cell, which `views::layout` and the flagged handlers read through `orgs_enabled()`: a nav list is built by a free function with no access to `AppState`, which is why the value lives in a cell rather than being threaded through every caller. A read that fails leaves the feature OFF and logs (`error` at startup, `warn` on a refresh) rather than guessing it on. The BUNYIP-487 copy guard in `bunyip-web/src/security.rs` stays absolute rather than becoming conditional on the flag: copy the feature adds is written fresh under the flag and must not reuse a banned string.

## At-rest encryption (BUNYIP-483, BUNYIP-491)

**At-rest encryption**: ONE key, `APP_ENCRYPTION_KEY` (+ `APP_ENCRYPTION_KEY_PREV`, a comma-separated list of keys old rows still need, + `APP_KEY_VERSION`), protects `user_totp`, `stripe_config` and `email_config` alike (BUNYIP-483). `Config::app_key_set()` builds the one `AppKeySet`; every encrypt/decrypt site takes it. Rewrite existing rows with `bunyip-api reencrypt-secrets` (idempotent); `scripts/check-no-retired-env.nu` fails the build if a per-consumer key name reappears. The list (rather than a single previous key) exists only for the consolidation window; narrowing it back to dunite's `EncryptionKeySet` is BUNYIP-491. Runbook: `docs/encryption-key-rotation.md`.

## Startup config validation (BUNYIP-537)

**Startup config validation**: every environment variable bunyip-api reads is classified in ONE table, `ENV_INVENTORY` in `crates/bunyip-domain/src/config.rs` (BUNYIP-537), as required / required-in-production / feature-gating / defaulted, each with the feature it gates and a remediation sentence. `Config::from_env` collects EVERY failure in one pass and returns `ConfigError::Startup(Vec<ConfigFailure>)`; `main.rs` logs one `tracing::error!` per failure and exits 1. A missing feature-gating variable gets one `tracing::warn!` from `log_feature_gaps()` (so the "feature is off" message lives in the inventory, never at the call site); a defaulted one logs nothing. `panic!` is never the reporting mechanism for missing or malformed configuration: use `ConfigFailure` in the domain crate and `fatal_config_error` in `main.rs`. `bunyip-api/tests/env_inventory.rs` fails the build on an unclassified `env::var("...")` / `secret_env("...")` read, on a `panic!` returning to those two files, and on a boot report that does not exit 1. Operator-facing rendering: `docs/configuration.md`.

## Configuration providers (BUNYIP-643, BUNYIP-537, BUNYIP-644)

**Configuration providers**: configuration comes from THREE declared providers in a fixed priority order, `database` > `file` > `environment` (`crates/bunyip-domain/src/config_providers.rs`, BUNYIP-643), and the highest-priority holder serves the key; when none holds it the built-in default stands. The `from_db_row` / `has_db_overrides` pair that used to apply the `email_config` / `auto_ban_config` / `tier_config` rows on top of the environment is GONE: each row builds a `DatabaseProvider` and `EmailConfig::resolve` / `AutoBanConfig::resolve` / `TierConfig::resolve` walk a `ConfigStack`, so the precedence is a declaration rather than the order two functions happened to be called in, and `the_undeclared_database_override_path_does_not_come_back` fails the build if either name reappears in production code. `CONFIG_KEYS` declares only the settings with MORE THAN ONE provider, exactly as `GovernedSecret` does for secrets: the Stripe ids, `pricing_enabled`, `orgs_enabled` and the visibility flags stay database-only columns and the feature toggles are database-only rows (a file provider must never be able to turn a feature flag on), and `SMTP_EHLO_NAME` / `APP_URL` / `APP_NAME` / `SUPPORT_INBOX_EMAIL` / `SUPPORT_IMAP_POLL_SECS` stay environment-only. Every key names an `ENV_INVENTORY` variable (`config_keys_name_an_inventory_variable`), so BUNYIP-537 remains the registry. The `file` provider is the ONE file-based layer (BUNYIP-644): a DIRECTORY at `BUNYIP_CONFIG_DIR`, default `/app/config`, one file per key, where a default directory that does not exist means the deployment has no file layer and an explicitly named directory that cannot be read reports `Enumeration::Unsupported` rather than reading as empty. `DatabaseProvider::set` REFUSES a `GROUP_ONE_KEYS` startup value with a `ConfigFailure` naming it, so the database can never be asked for the credential used to reach the database. `bunyip-api config-status [--json]` is the configuration twin of `secrets-status` and prints per-key provenance and one of `use` / `default` / `overridden` / `shadowed`, the same 2x2 as `secrets::classify`, never a value; only `overridden` logs at boot (one `warn!` per ignored provider), because `shadowed` is how an override is meant to work when the precedence is an ORDER rather than one declared provider. The YAML file `sys_config.rs` used to keep at `BUNYIP_CONFIG_FILE`, below the environment, is GONE as a layer: `migrate_legacy_file` folds it into the directory once and renames it aside, dropping (with a `warn!`) any key the environment already held, so no deployment's resolved values move. Its four settings (`SYSTEM_SETTINGS_KEYS`) are ordinary declared keys now, and the admin System page writes them through `SystemSettings::entries`, the only field-to-file mapping in the crate, which by TYPE has no field for a system-level key: `system_level_keys_never_enter_the_file_layer` fails the build if one becomes writable or becomes a declared key, and `no_production_code_writes_the_legacy_yaml_format` fails it if a second on-disk shape comes back. The rate-limit caps resolve through this same stack (BUNYIP-645): their `RATE_LIMIT_*` names are built from the action, so their `CONFIG_KEYS` and `ENV_INVENTORY` entries are generated from `RateLimitConfig::ALL` rather than written down, and `rate_limit_configs` is their database provider. Operator reference: `docs/configuration.md`.

## Secret sourcing (two tiers) (BUNYIP-38, BUNYIP-542, BUNYIP-642)

**Secret sourcing (two tiers)**: Group-1 startup secrets (postgres, `DATABASE_URL`, `APP_ENCRYPTION_KEY`, `JWT_SECRET`, ...) are file-based: the app reads `/run/secrets/*` via the `{NAME}_FILE` convention (BUNYIP-38), provided directly by `scripts/init-secrets.nu` (dev throwaways) or the SOPS `compose-secrets.yml` on the docker hosts. They cannot be governed by the switch below (the database cannot hold the credential used to reach the database), are never fetched from or synced with Infisical, and so Infisical is never needed to boot. Group-2 governed integration secrets are exactly the four with more than one possible provider (`SMTP_PASSWORD`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `SUPPORT_IMAP_PASSWORD`), and ONE required variable declares which provider holds them: `SECRETS_STORAGE=environment|database|infisical` (BUNYIP-542). The declared provider is the ONLY one consulted; the old DB-then-env-then-Infisical precedence chain is deleted, not reordered. At boot each governed secret is used if the declared provider holds it, warns (feature off) if no provider does, warns per duplicate if another provider also holds it, and is FATAL if the declared provider is empty while another provider holds it. `environment` mode reads `{NAME}_FILE` only (never the plain variable, which `docker inspect` exposes) and is the one read-only provider, so the admin secret fields render read-only and the API answers 409; `database` and `infisical` mode write through to the declared provider and hot-reload. `infisical` mode is fail-closed at boot; the other two never contact Infisical. `crates/bunyip-domain/src/config.rs` owns `SecretsProvider` / `GovernedSecret`, `bunyip-api/src/secrets.rs` owns every provider read and write plus the `bunyip-api secrets-status` / `secrets-migrate --to <mode>` / `secrets-purge --confirm` pre-flight family. The vocabulary is provider throughout (BUNYIP-642), while the `SECRETS_STORAGE` variable, the three subcommand names, the `secrets-status --json` keys and the `secrets_storage` admin-API field deliberately keep their spellings: renaming any of them breaks a running deployment or a script for no functional gain. Runbook: `docs/secrets-infisical.md`; per-mode reference: `docs/configuration.md`.

## Settings archive (BUNYIP-714)

**Settings archive**: every admin-managed database setting moves as ONE passphrase-encrypted file through `bunyip-api/src/settings_archive.rs` and the `bunyip-api settings-export` / `settings-import` pair (BUNYIP-714), because the configuration that makes a rebrand or a cap change need no deploy is exactly what a wiped postgres volume takes with it, and a `pg_dump` is the wrong instrument (it carries the users, the sessions and the audit log too, and its encrypted secret columns travel without the key that reads them). The format is a version-1 JSON envelope carrying its own Argon2id parameters and salt plus an AES-256-GCM ciphertext: the key is derived from the passphrase inside an `argon2_offload::offload` closure, the archive reuses `EncryptionKeySet` / `decrypt_with_key` rather than a new crypto crate, and the governed secrets are resolved to plaintext at export so the file opens without `APP_ENCRYPTION_KEY` or the old database. No flag takes the passphrase (argv is in the process list): it comes from `--passphrase-file <path|->`, export refuses one under 16 characters or scoring below zxcvbn 4 (the brand name and the `APP_URL` host are fed in as known words) while import checks nothing, `--output` refuses an existing path and creates the file 0600, and neither path is ever `-`. Import is REPLACE, not merge: a section present ends up holding exactly the archive's rows (existing key updated in place keeping its id and cascaded children, missing inserted, target-only DELETED) and a section absent is untouched, which is what makes it idempotent. Both subcommands refuse a `_sqlx_migrations` version that disagrees with `sqlx::migrate!`'s last, import refuses an archive from another schema version, every row is validated through the admin path's own `validate_branding` / `visible_without_price_error` / `validate_limits` / `refuse_disabled_email_in_production` BEFORE any write, the database half is ONE transaction with the two steps that cannot join it (governed secrets, the file layer) reported per step, and a verification pass re-reads everything. A plan or report names sections, columns, keys and counts and NEVER a value: `a_rendered_plan_carries_no_setting_value` gates that, and `every_column_of_every_archived_table_is_carried_or_declared_excluded` in `bunyip-api/tests/settings_archive.rs` reads `information_schema.columns` and fails the build on a column that is neither archived nor in the module's declared exclusion list, so a migration cannot silently drop a new setting from every export. Operator reference: `docs/settings-archive.md`.
