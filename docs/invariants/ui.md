# UI

Full text of the UI conventions indexed in [`CLAUDE.md`](../../CLAUDE.md#critical-conventions), moved here verbatim (BUNYIP-854).

## Scrollbars (BUNYIP-848, BUNYIP-509, YOTUN-208)

**Scrollbars**: every scroll container gets a thumb-only scrollbar that hides at rest (BUNYIP-848, superseding BUNYIP-509's always-visible rule while keeping its 14px grab zone): no painted track or background in any theme, a 5px pill (8px on hover or drag) inside a 14px `::-webkit-scrollbar` strip, colored `hsl(var(--muted-foreground) / var(--sb-alpha))`. `bunyip-web/assets/js/app.js` sets `data-scrollbars="auto"` on `<html>` and marks a container `[data-scrollbar-active]` while it scrolls, while a mouse or pen is in its 14px strip, and for a whole thumb drag, then removes the mark `SCROLLBAR_IDLE_MS` (6s) after the last activity; the thumb glides in over 150ms and out over 400ms, and `prefers-reduced-motion: reduce` drops the glide but not the hold. The hidden rest state applies only under `html[data-scrollbars="auto"]` and `@property --sb-alpha` starts at 1, so a page whose script never ran keeps its bars visible (fail visible). Chromium and Safari are styled through `::-webkit-scrollbar*` alone: any `scrollbar-width` / `scrollbar-color` they see makes Chromium 121+ drop the webkit rules (YOTUN-208), so those two live only in the Firefox `@supports not selector(::-webkit-scrollbar)` block, the one place `thin` is allowed. Never `scrollbar-width: none`, `display: none` on a scrollbar pseudo-element, or a painted track, bar or corner. Editing `input.css` means rebuilding the committed `bunyip-web/assets/styles.css` (`bun run build:css` in `bunyip-web/`) in the same PR; `scripts/check-scrollbars.nu` gates both stylesheets and the `app.js` constant in `check.yml`.

## Committed CSS is current (BUNYIP-598, BUNYIP-566)

**Committed CSS is current**: `bunyip-web/assets/styles.css` is committed and served as-is, so `scripts/check-css-current.nu` rebuilds it to a temporary path and fails the build unless the result is byte-for-byte the committed file (BUNYIP-598). It also fails when a `crates/*/src` directory containing `class="` is not named by an `@source` line in `bunyip-web/input.css`: Tailwind's automatic source detection is rooted at `bunyip-web/`, so a crate outside it is never scanned and its classes are silently dropped from the next rebuild, which is how the web-kit extraction lost 34 utilities into a stale artifact (BUNYIP-566). The guard only ever reads the committed file (it digests it either side of the build), and uses the runner's `bun` when there is one, else the `rust-builder-glibc` image `just check-container` uses. `just check` and `check.yml` both run it.

## UI copy (BUNYIP-551, BUNYIP-624)

**UI copy**: one name per admin section in Title Case across the sidebar (`admin_items()` in `bunyip-web/src/views/layout.rs`), the topbar title (the `admin_response` argument) and the page h1; route paths never move with a rename. Ellipses are the single-character `…`, never three dots, and empty states are terse noun phrases with no emoticon and no apology (BUNYIP-551). An internal issue key never appears in copy a user reads: it belongs in the code and in comments, so the admin help text carries the sentence and the reference sits in a comment beside it (BUNYIP-624). `scripts/check-ui-copy.nu` gates those three in `check.yml`, exempting log lines, assertion messages and anything from `#[cfg(test)]` on, where a reference is what makes the output traceable; a unit test in `layout.rs` gates the casing.

## Prices and deadlines in copy (BUNYIP-590)

**Prices and deadlines in copy**: a price a user reads comes from the published `/v1/pricing` payload, never a literal: `util::entry_price` is the cheapest monthly tier a visitor can still buy (lifetime and sold-out tiers excluded) and prices the signup card and the membership-required page; `util::tier_price` prices the member's own tier on the plan card, except when `price_locked`, where the member's `locked_price_amount` wins because a locked price is exactly the one the current tier price need not equal. The past-due dunning banner (`dunning_banner` in `handlers/dashboard.rs`) names that member's `grace_period_end`, not the fixed "within 30 days" it used to promise. Absent value means NO number, never a substituted one: "Get access to all tools", "See pricing", "before your grace period ends" (BUNYIP-590). `scripts/check-price-literals.nu` fails the build on a price per period or a `within N days` in any string literal under `bunyip-web/src` or `crates/web-kit/src` unless the line carries a `// price-literal-ok: <reason>` marker, and gates it in `check.yml`.

## Password inputs (BUNYIP-282, BUNYIP-575, BUNYIP-596, BUNYIP-597)

**Password inputs**: every form where a user types a password renders `views::password::password_field`, so the characters can be revealed and checked (BUNYIP-282), and every form where a user CHOOSES one also carries `data-pw-guard` plus `views::password::guard_message()` and `script()` (BUNYIP-575). A rejected password change answers with a redirect, and a redirect re-renders every `type=password` input EMPTY (a server-known password is never written back into HTML), so `assets/js/password-field.js` refuses the submit while a rule the browser can check itself is broken and names that rule inline instead; `handlers::password_ok` stays the backstop for a client with no JS. The live per-rule indicators and the HaveIBeenPwned lookup stay in the separate `assets/js/password.js`, so a form can take the toggle and the guard without also depending on an external service; a card renders `pw_reqs()` (the `id="pw-reqs"` list) and that script together or neither, because dead indicators read as a live check that already passed (BUNYIP-596). Only a confirmed breach hit (`pw-fail` on `pw-breach`) blocks the submit: a lookup that could not run logs a `console.warn` and falls open, so a HaveIBeenPwned outage never blocks sign-up or password reset, while a lookup still in flight holds the gate shut so it cannot open ahead of the answer. `every_card_that_sets_a_password_reveals_it_and_guards_the_submit` and `every_card_that_renders_the_password_rules_ships_their_controller` in `handlers/auth_pages.rs`, plus the two `change_password_form_*` tests in `handlers/dashboard.rs`, fail the build if a surface loses either half. The reveal half is enforced repo-wide rather than per-card: `no_handler_hand_rolls_a_password_input` in `bunyip-web/src/views/password.rs` scans `handlers/auth_pages.rs`, `handlers/dashboard.rs` and `handlers/admin/applications.rs` line by line and fails the build on a `type="password"` outside the helper, so the identity confirmations (sign-in, Change Email, Disable 2FA, Delete My Account, regenerate recovery codes, reset authenticator app, admin application delete) cannot go blind again (BUNYIP-597). The four masked secret displays in `handlers/admin/email_config.rs` (`smtp_password`, `imap_password`) and `handlers/admin/stripe.rs` (`secret_key`, `webhook_secret`) are the deliberate exception that scan does not cover: they are `readonly` / `disabled` masks of a STORED secret, not of what the user is typing. The helper's fifth argument is a `PwField` options struct (`autofocus`, `required`, an `autocomplete` override and a `label_suffix`), which is how a confirmation keeps the attributes its hand-rolled input had; the `autocomplete` override is the load-bearing one, because a control-level `current-password` beats the `autocomplete="off"` on the form, so the change-email and delete-account forms pass `Some("off")` to suppress password-manager pre-fill.

## Authenticated navigation (BUNYIP-547, BUNYIP-630)

**Authenticated navigation**: both app shells build their nav from one list, `shell_nav_sections()` in `bunyip-web/src/views/layout.rs`, rendered by `nav_links()` into two surfaces: the `hidden md:flex` `sidebar()` and the `md:hidden` `mobile_nav()` disclosure in `app_topbar` (BUNYIP-547). The sidebar is not rendered below 768px, so an entry added anywhere but that shared list is unreachable on a phone. `mobile_nav` is a `<details data-menu>`, the same pattern `profile_menu` uses, so `assets/js/app.js` already dismisses it on click-away and Escape; no new script. `every_authenticated_shell_navigates_below_the_md_breakpoint` in `layout.rs` strips the sidebar from each shell's markup and asserts every nav `href` still renders. The one exception to "that shared list or nowhere" is `TOPBAR_DESTINATIONS` (BUNYIP-630): the handful of destinations a signed-in visitor reaches most (`/applications`, `/docs`) are ALSO rendered by `topbar_link()` directly into `app_topbar`'s right-hand cluster, beside `theme_controls`, so they cost one click instead of a disclosure open. Those entries carry NO breakpoint class, which is what makes them survive the below-`md` collapse, and they link rather than fetch, so no chrome payload can empty one. Promotion never removes the `shell_nav_sections` row, so the sidebar stays the complete destination list and every existing path keeps working; `every_authenticated_shell_puts_the_top_bar_destinations_one_click_away` fails the build if a shell drops an entry, hides one behind the disclosure, gates one on a breakpoint, leaves one without an accessible name, or removes its nav row.

## Theme tokens (BUNYIP-549, BUNYIP-568)

**Theme tokens**: every surface is painted from the semantic tokens, client-side markup included. The toast pills in `bunyip-web/assets/js/app.js` use the same token pair as their server-rendered counterparts (success the `success` badge in `views/ui.rs`, error the offline banner in `server_status.rs`, info the popover surface), so they track `.dark` and `.high-contrast`; `input.css` remaps only `indigo` and `teal`, so any other stock Tailwind scale is a colour no theme class reskins. The framework shell (`document()` in `views/layout.rs`) carries no colour literal: the two `theme-color` metas come from the branding record's `theme_color_light` / `theme_color_dark` columns, so a skin moves the browser chrome with the rest of the palette (BUNYIP-549 / BUNYIP-568). `scripts/check-theme-colors.nu` gates both in `check.yml`; a unit test in `layout.rs` gates the metas. Changing a class name in `assets/js/` means rebuilding the committed `bunyip-web/assets/styles.css` in the same PR, exactly as editing `input.css` does.

## A button's `extra` never fights its variant (BUNYIP-656)

**A button's `extra` never fights its variant** (BUNYIP-656): `button_class(variant, size, extra)` concatenates `BTN_BASE`, the variant, the size and the caller's `extra`, and CSS resolves two same-specificity utilities by their order in the STYLESHEET, not their order in the class attribute. So an `extra` that names a property the variant already names overrides it only when Tailwind happens to emit it last, which is luck and not a rule: the public CTA passed `bg-white text-brand-primary-800` to the `default` variant, `bg-white` sorted after `bg-primary` and won while `text-brand-primary-800` sorted before `text-primary-foreground` and lost, so the button shipped a white label on a white pill and read as an empty box (the arrow went with it, `stroke="currentColor"`). Needing a different colour or size means a new VARIANT or SIZE in `variant_classes` / `size_classes`, never an `extra`: that is what `inverse` (the light fill on the brand gradient), `brand` (the skinnable `--skin-primary-*` fill, where `bg-primary` is a static hex that a rebrand does not move) and the `xs` size are. `every_button_extra_outranks_the_variant_colour_it_overrides` in `views/ui.rs` scans every `button_class` call in both source trees, reads each utility's declared CSS properties out of the built `assets/styles.css`, and fails when a variant token and an extra token set the same property in the same state and the stylesheet emits the variant's last. It reads the real cascade rather than a list of colour-utility names, so `text-xs` (font-size) and `bg-gradient-to-r` (background-image) are not conflicts and no name list can rot.

## Amber contrast (BUNYIP-548)

**Amber contrast**: amber is the one stock scale the views paint text in, and a tint of it (`bg-amber-500/<n>`) lightens the surface under that text, so the ratio is measured against the composite, not the bare surface. Light halves use `amber-800` on a tint and `amber-700` bare; dark halves use `amber-300` / `amber-400` (BUNYIP-548). `every_amber_text_use_meets_aa` in `views/ui.rs` scans every source line carrying an amber text class and asserts AA 4.5:1 over `--card` and `--background` in all four theme blocks, reading the palette from the built `assets/styles.css`, so a new amber surface fails the build rather than shipping under AA.

## Fetched list states (BUNYIP-461, BUNYIP-546, BUNYIP-635)

**Fetched list states**: every surface that renders a fetched collection tells three states apart, in this order: `@if !reachable { error_box("Could not reach the API to load <thing>.") } @else if items.is_empty() { empty_state(...) } @else { ... }`. `reachable` is the `data.is_ok()` flag kept beside the `unwrap_or_default()` at the fetch site (BUNYIP-461 for the admin lists, BUNYIP-546 for the member and public ones). A card is never hidden on failure or on empty: hiding it makes "could not load" and "nothing configured" indistinguishable from "everything is fine". Substituting an empty page for a failed fetch is the same defect in another shape, so `handlers/dashboard.rs` passes `Option<&PaginatedResponse<_>>` into its card bodies and `no_empty_page_fallback_absorbs_a_fetch_error` fails the build if that fallback returns. A fetch that only decorates another list (application groups, per-product downloads) may degrade silently in the UI, but logs `tracing::warn!` naming the degradation. One surface omits its EMPTY state and only its empty state: the `/docs` hub's application-documentation section and its section menu drop the heading when no application publishes documentation (BUNYIP-635), because a public docs page has nothing to tell a visitor there. The failure state is unchanged and still visible, which is the half of the rule that exists to keep a broken fetch from reading as "everything is fine", and `an_unreadable_application_list_says_so_instead_of_reading_as_empty` in `skin/content.rs` fails the build if it regresses.

## Toast dismissal (BUNYIP-610, BUNYIP-98)

**Toast dismissal**: `window.bunyipToast` in `bunyip-web/assets/js/app.js` is the last layer a failure crosses, so an `error` pill schedules NO auto-dismiss timer and stays until the user clicks its close button; `success` and `info` scale with the message, `TOAST_LONG_MS` (8s) past two whitespace-separated words and `TOAST_SHORT_MS` (5s) at two or fewer, replacing the flat 2500ms that cut a relayed API error off mid-read (BUNYIP-610). Every pill carries a real `<button aria-label="Dismiss">`, and the button and the timer share one `dismissToast` (the unchanged 250ms fade, then detach), so an early dismissal looks identical to an expiry. BUNYIP-98's 5-pill cap still evicts the oldest of every kind. The `?toast_ok=` / `?toast_err=` draining needs no change: it already routes through `bunyipToast`. `error_toasts_wait_for_a_click_and_the_others_scale_with_the_message` in `views/layout.rs` reads the constants out of the shipped script and fails the build if a timer reaches an error pill or the boundary moves.
