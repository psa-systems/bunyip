# Branding and email

Full text of the branding and email conventions indexed in [`CLAUDE.md`](../../CLAUDE.md#critical-conventions), moved here verbatim (BUNYIP-854).

## Email templates

**Email templates** are `include_str!`-compiled into `bunyip-domain`; the product name in every subject and in the template `app_name` context comes from the admin-managed branding record (see the branding bullet below), NOT from `APP_NAME`, which is only its bootstrap default. `BASE_URL` (`APP_URL`) stays env-derived.

## Branding (BUNYIP-561)

**Branding**: the product name, tagline, meta description and Open Graph image are ONE admin-managed row, `branding` (id = 1), and no product copy is compiled into either binary or set in compose (BUNYIP-561). `brand_name` resolves to the row value when non-empty, else bunyip-api's `APP_NAME` (a bootstrap default for a database that has never been branded); the other three resolve to the row value or to EMPTY, and empty means the markup is OMITTED - never substituted with a literal, because substituting one puts the copy back in the binary. `crates/bunyip-domain/src/models/branding.rs` owns the model, the validator and the `BrandingCache`; `EmailService` and `TotpService` read the name from that cache (so a rename reaches the next email subject and the next TOTP enrolment without a restart, and existing `user_totp` rows are never migrated). Public `GET /v1/branding` (under the `RateLimitFloor`, not in `EXEMPT_PATHS`) plus admin `GET`/`PUT /v1/admin/branding`; a `PUT` writes the row and refreshes the api-side cache in the same request, and every other api process re-reads it every 60s. bunyip-web has NO `APP_NAME` / `BRAND_DESCRIPTION`: `bunyip-web/src/branding.rs` fetches `/v1/branding` once before the listener binds (a failure logs `error` and serves unbranded) and refreshes every 60s (a failure logs `warn` and keeps the last good values), and `views::layout::document()` renders `og:`/`twitter:` metadata from it, each tag omitted when its source is empty. `scripts/check-brand-literals.nu` fails the build on a standalone `Bunyip` in the trees named by its `GUARDED_GLOBS` (currently `bunyip-web/src/{views,handlers,skin}/**/*.rs`, `bunyip-web/src/skin/docs/**/*.md` and `crates/web-kit/src/**/*.rs`) unless the line carries a `// brand-literal-ok: <reason>` marker. Operator reference: `docs/configuration.md`.

## Brand assets and the palette (BUNYIP-560, BUNYIP-553)

**Brand assets and the palette** (BUNYIP-560): the same record carries `theme_css` / `theme_color_light` / `theme_color_dark` plus three image slots, so a rebrand needs no rebuild. The images are rows in `branding_assets` (bytes in a `BYTEA`, the `user_avatars` pattern), uploaded through `POST`/`DELETE /v1/admin/branding/assets/{mark|favicon|mascot}` and served unauthenticated from `GET /v1/branding/assets/{kind}`, which bunyip-web proxies same-origin at `/brand/{kind}?v=<version>` (`branding::BRAND_ASSET_KINDS` is the allow-list that stops the path segment addressing another endpoint). The favicon slot stores what was uploaded as `favicon-source` and DERIVES the whole set from it in ONE transaction (`bunyip-api/src/branding_assets.rs`, the `image` crate, on the blocking pool per BUNYIP-553), so a half-replaced icon set is unreachable and one upload answers every `<link rel="icon">`. Fallbacks differ per slot and are stated in `views::layout::FAVICON_LINKS` / `brand_mark` / `skin::public::hero_mascot`: the favicon set falls back to the committed files under `bunyip-web/assets/` (root `/favicon.ico` included, served by `branding::favicon_ico`), the mark falls back to the built-in glyph, and the mascot falls back to the committed `bunyip-hero-448.webp` / `bunyip-hero-718.webp` pair under `bunyip-web/assets/` (BUNYIP-605), the same "committed file, admin upload overrides" shape as the favicon set and the mark. The record is the ONLY source of the palette: the three brand-theme bootstrap environment variables BUNYIP-560 kept for one release are gone with the plumbing that read them (BUNYIP-568), so `Config` holds no palette field, web-kit's shell holds no palette cell, and `web_kit::shell::palette_value` is "the row value, else omit". The `#2f4e2e` / `#161a16` pair is gone from the binary, `scripts/check-theme-colors.nu` gates `bunyip-web/src/config.rs` and `crates/web-kit/src/shell.rs` as well as `views/layout.rs` so none can carry a colour literal again, and `scripts/check-no-retired-env.nu` names those three variables as retired and fails the build if one reappears in a tracked file.
