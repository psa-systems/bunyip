# API and web boundary

Full text of the API and web boundary conventions indexed in [`CLAUDE.md`](../../CLAUDE.md#critical-conventions), moved here verbatim (BUNYIP-854).

## Mailer relay (BUNYIP-602, BUNYIP-603, BUNYIP-604)

**Mailer relay**: `POST /v1/mailer/send` is the send-only API the other apps in the suite call instead of holding their own SMTP credentials (BUNYIP-602). The caller is a CALLING APP, not a person: it presents its `oauth_clients` machine credential (`client_id`:`client_secret`) as HTTP Basic, and `bunyip_oidc::machine_client` verifies it through the same `authenticate_client` the token endpoint uses, so a machine credential is registered, rotated and revoked in exactly one place. The secret is checked BEFORE the `client_credentials` entitlement, or the 403 becomes an oracle naming which registrations exist. `machine_client::load_machine_client` takes the pool rather than an `OidcProvider`, so the relay needs no issuer and no key material. The endpoint is in `rate_limit_floor::EXEMPT_PATHS` because the suite's apps share egress and the per-IP floor would let one app throttle another; `RateLimitConfig::MAILER_SEND` (60/min per `client_id`) and `MAILER_AUTH_FAILURES` (10/min per IP, failures only, read-only-checked ahead of the ~100 ms Argon2) are the controls that replace it. The `From:` identity is always this deployment's verified sending address, never the caller's, and a CR/LF in `to` or `subject` is refused rather than stripped. A deployment with no SMTP transport answers 502 and logs at `error`: the relay never takes a message and drops it, because the calling app has handed off responsibility for delivery. `EmailService::new_capturing` is the mocked transport the tests drive; `no_binary_wires_the_capturing_transport` in `bunyip-api/src/handlers/mailer.rs` fails the build if it reaches a binary. The suppression seam (`SuppressionList` / `NoSuppression` in `crates/bunyip-domain/src/services/mailer_relay.rs`) runs before every send and is filled by BUNYIP-603. Provisioning is the `bunyip-api machine-client register` / `rotate` / `disable` / `list` subcommand family (`bunyip-api/src/machine_client.rs`, BUNYIP-604), the supported replacement for the hand-written `INSERT` plus an out-of-band Argon2 hash that shipped one never-completed registration: it generates the secret, hashes it with the verifier's own `machine_client::hash_client_secret`, and RETURNS the report rather than printing it, so the plaintext reaches stdout in `main.rs` once and no log, file or column ever holds it (`Secret` redacts its own `Debug`, and `this_module_never_logs` fails the build if a logging or printing macro appears in that module). Operator reference: `docs/mailer-relay.md`.

## Unknown hosts (DEV-741, BUNYIP-686)

**Unknown hosts**: wildcard DNS sends every `*.{app_domain}` label to the edge proxy, and a lowest-priority Traefik catch-all router (in the `NiceGuyIT/docker` repo, DEV-741) forwards any single-label host no other router claims to bunyip-web with `X-Bunyip-Unknown-Host: 1`. `skin::public::unknown_host_gate`, layered right after the router fallback in `main.rs` (inside CSRF and CSP), answers such a request with a 404 page that links to `Config::apex_url()` and redirects there after 10 seconds through `app.js`'s `data-redirect-to`, never a 301/302, which would make every label a live alias of the main domain (BUNYIP-686). It passes `/assets/`, `/brand/` and `/favicon.ico` through so the page's own resources stay same-origin under `script-src 'self'`, and it takes only `Arc<Config>`, so an unknown-host hit never reaches `/v1`. bunyip-web itself has no Host allowlist: without the header it serves the site on any Host, which is why the header, not a Host comparison, decides (dev-sso runs `BUNYIP_APP_DOMAIN=localhost` behind a per-developer `*.a8n.run` host). A bunyip-web release carrying the gate must be deployed before the proxy labels, or unknown hosts get the full site with a 200.

## Wire compatibility (BUNYIP-506)

**Wire compatibility**: every field of a `Deserialize` response struct in `bunyip-web/src/api/types.rs` carries `#[serde(default)]` unless it is listed in the `ESSENTIAL_FIELDS` table of `scripts/check-serde-compat.nu` with its reason (identifiers, tokens and URLs whose absence must keep failing loudly). Wire enums decode through `String` via the `wire_enum!` macro, so an unrecognised value becomes `Unknown` rather than failing the response. Renaming a wire key follows expand/contract over two releases: release N emits both keys and the client reads the new one with `#[serde(alias = "<old>")]`; release N+1 drops the old key and the alias. The rule is asymmetric by direction - request structs in `bunyip-api/src/handlers/` keep required inputs required so a malformed request still 400s, and take the alias rule only. A 2xx body that will not decode logs `tracing::error!` with endpoint + target type and shows one fixed line (BUNYIP-506).

## Cookies (BUNYIP-426)

**Cookies**: the `Secure` attribute comes from `Config::cookies_secure(&req)` (transport-derived), never from `Config::is_production()` (BUNYIP-426 F4). Any new set-cookie site must use it.

## Single-use tokens (BUNYIP-426)

**Single-use tokens** are consumed by a guarded `UPDATE ... WHERE id = $1 AND used_at IS NULL` whose `rows_affected` decides the race; the caller branches on the returned bool before doing side-effecting work (BUNYIP-426 F9). A unit test in `repositories/token.rs` fails the build if an unguarded consume reappears.

## OCI errors log their cause (BUNYIP-565)

**OCI errors log their cause**: every failure in `crates/bunyip-oci/src` that becomes `OciError::Internal` is routed through `crate::errors::context` (BUNYIP-565), the one module that constructs that variant. `OciErrorContext::internal_ctx` takes a closure that names the operation (the slug, digest or user id in scope) and logs at `tracing::error!` before returning the internal error, so a registry 500 always leaves one line naming what was being attempted; `internal_fault` covers a wiring gap that has no source error to log. The wire vocabulary and its status codes never move, because `dunite_oci::errors::oci::OciError` pins them (that crate is the engine this vertical wires; see `bunyip-oci/Cargo.toml` and `bunyip-oci/src/lib.rs`). `every_internal_error_logs_its_cause_first` in `crates/bunyip-oci/src/errors/context.rs` fails the build on a `map_err(|_| ...)` that drops the cause anywhere in the vertical, and on an `OciError::Internal` built outside that module.
